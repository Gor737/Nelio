`docs/architecture.md` and `docs/decision.log.md`; the choices made where those were silent are in `docs/proposed-defaults.md`.

## 4. Choosing the production hosting provider (OPEN: owner decision)

Nothing below has been verified for any provider. Before deploying, confirm each point **from the provider's own documentation**, and record the answer:

1. **PostgreSQL 18 or later is offered.** `uuidv7()` is a core function in 18; no extension is installed for it (Decision 165). The schema fails to build on an older server.
2. **`pg_trgm` is allowed** (the user-name search uses a trigram index).
3. **Advisory locks and `set_config(..., true)` behave correctly behind the provider's connection pooler.** The application uses `pg_advisory_xact_lock` and transaction-local settings (`SET LOCAL` / `set_config(.., true)` for the lock and statement timeouts) inside interactive transactions. Both are transaction-scoped, so they are safe in *transaction* pooling mode and in direct connections; they would be wrong in *statement* pooling mode. Prisma's pool is already client-side: with a server-side pooler, put the pooler in transaction mode and check the Prisma/driver notes on prepared statements.
4. **Backups and a tested restore are possible** (section 8). Deleted-message text persists in backups (Decision 86).
5. **S3-compatible private and public bucket policies are possible** (section 7).
6. **Pool size.** One backend instance uses at most `POOL_MAX` (10) connections; `prisma migrate deploy` and the seed use one more each, briefly. Compare 10 + a margin with the provider's connection limit for the plan chosen, and change `TRANSACTION_LIMITS.POOL_MAX` in code (it is deliberately not an environment variable) only if the limit requires it.

## 5. Building and starting

```bash
cd apps/backend
npm ci
npm run prisma:generate        # the generated client is not committed; the build needs it
npm run build                  # nest build -> dist/
npm run db:migrate:deploy      # applies prisma/migrations (forward-only); run with the production DATABASE_URL
npm run seed:admin             # first deployment only; see section 9
NODE_ENV=production npm run start:prod    # node dist/main; no .env file is read
```

`npm run smoke:prod` (run after `npm run build`, with `DATABASE_URL` of a reachable database) starts `dist/main` the way `start:prod` does and checks: an
incomplete production environment exits with a message naming every missing setting and no stack trace or value; a valid one starts, answers `GET /health`
(`{"status":"ok","database":"up"}`), serves the API, hides the Swagger UI (`/api/docs`, `/api/docs-json` are 404), sends the Helmet headers and no
`X-Powered-By`, names the configured origin in CORS, refuses protected routes without a token; SIGTERM stops it within seconds; the log is JSON lines and
contains neither the JWT secret nor the storage secret. It only reads the database.

## 6. Environment reference

`.env.example` (repository root) is the source; `test/release/env-completeness.spec.ts` keeps it complete. In production **no `.env` file is read**: set real environment variables.

| Variable | Production | Meaning |
|---|---|---|
| `NODE_ENV` | `production` | turns Swagger off, requires everything marked required, forbids development defaults |
| `DATABASE_URL` | **required** | PostgreSQL 18+ URL |
| `JWT_SECRET` | **required** | at least 32 bytes, not a placeholder (`openssl rand -base64 48`). Rotating it logs everyone out |
| `FRONTEND_ORIGIN` | **required** | exact origin of the frontend (`https://app.example.com`), no path, never `*` |
| `TRUST_PROXY` | set it | number of reverse proxies in front of the backend (0-10). Wrong values make the rate limiter see the proxy's address |
| `PORT`, `LOG_LEVEL` | optional | default 3000, `info` |
| `SWAGGER_ENABLED` | optional | off in production unless `true` |
| `SMTP_HOST`, `MAIL_FROM` | **required** | plus `SMTP_PORT`, `SMTP_SECURE`, and `SMTP_USER` / `SMTP_PASSWORD` (both or neither). STARTTLS is required in production |
| `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_BASE_URL` | **required** | `S3_ENDPOINT` may be left out for AWS-style stores; `S3_REGION`, `S3_FORCE_PATH_STYLE` optional. Production never falls back to `MINIO_ROOT_*` |
| `GOOGLE_CLIENT_ID` | optional | without it the three Google endpoints answer 503 |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `SEED_ADMIN_NAME` | first run only | remove the password afterwards |

**Same-site deployment.** The refresh cookie is `HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth`. Serve the frontend and the API from one registrable
domain (for example `app.example.com` and `api.example.com`) or behind one reverse proxy, over HTTPS. The proxy must set `X-Forwarded-For`; set `TRUST_PROXY`
to the number of proxies. `Secure` cookies are not sent over plain HTTP (in development, `http://localhost` is treated as secure by Chrome and Firefox only).

## 7. Object storage policy

Keys are generated by the server: `public/avatars/<uuid>.<ext>` and `public/covers/<uuid>.<ext>` (read by anyone through `S3_PUBLIC_BASE_URL`), and
`private/attachments/<uuid>.<ext>` (served only through signed URLs that last 5 minutes). Uploads go through the API server, never from the browser.

- Block all public access to the bucket as a whole, then allow **anonymous `s3:GetObject` on `public/*` only**.
- `private/*` has no anonymous access. The application's access key needs `s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` on the bucket's objects and nothing else.
- No browser CORS rule is needed for uploads (they go to the API); the browser only `GET`s public images and signed attachment URLs, which need no CORS for `<img>` or navigation.
- Check from outside the account: a `public/` object is readable without credentials, a `private/` object is not, and a signed URL stops working after 5 minutes.

## 8. Backups and a tested restore

- Take backups with the provider's managed backup service (point-in-time recovery if offered) **and** keep the ability to take a logical dump: `pg_dump --format=custom --no-owner --no-privileges`.
- **A backup that has not been restored is not a backup.** `npm run db:restore-rehearsal` dumps `DATABASE_URL`, restores it into a scratch database it creates (`nelio_restore_rehearsal_<random>`, the only name it will create or drop), compares the tables and the row count of every table, the migration history, the constraint and index counts, and checks that `pg_trgm`, `uuidv7()` and the audit-log immutability trigger survived; then it drops the scratch database. It only reads the source. The client tools must be the same major version as the server or newer (`pg_dump` refuses an older one); where the host has an older client, set `REHEARSAL_DOCKER_CONTAINER=<postgres container>` to run them inside the database container.
- It was run for this release against the test database (25 tables, all counts equal). Repeat it against the production database after the first real backup, and once on the chosen provider's own restore flow.
- Deleted-message text persists in the database and its backups (Decision 86); retention of backups is therefore a privacy decision.
- Migrations are forward-only. To undo a bad release, restore the pre-release backup or write a new migration; never edit an applied migration.

## 9. Runbook

**Start-up.** The process exits with code 1 and a list of problems (names only, never values) if the configuration is invalid. `GET /health` is `200 {"status":"ok","database":"up"}` or `503` when the database is not reachable.

**Create the first Admin.** `SEED_ADMIN_EMAIL=... SEED_ADMIN_PASSWORD=... npm run seed:admin` (after the build and migrations). It creates the user with a verified email, the STUDENT and ADMIN roles, only when no active Admin exists; running it again changes nothing; an email that is already registered is refused. Later Admins: `PUT /api/v1/admin/users/:id/admin-role`. If the only Admin is locked out, `forgot-password` works for them; if no active Admin exists at all, `seed:admin` creates one.

**Nightly jobs** (UTC, one backend instance only): 03:10 Auth tokens, 03:20 orphan files, 03:30 notification retention, 03:40 channel reconcile, 03:50 completion recheck. Log events (JSON lines, field `event`):

| Event | Level | Meaning | Action |
|---|---|---|---|
| `job_finished` | info | a job ran; `durationMs` | none |
| `job_failed` | error | a job threw; `error` is the error name | look at the database and the previous lines; the next night retries |
| `job_skipped_overlap` | warn | the previous run was still going | investigate if it repeats (slow database) |
| `channel_reconcile_repaired` | **warn** | the channel reconcile found drift and repaired it (`added`, `removed`) | **a bug**: a path changed enrollments or the team without syncing the channel. Find it |
| `completion_recheck_repaired` | **warn** | the completion recheck completed enrollments the request paths had missed | **a bug**: a path forgot a completion trigger. Find it |

The two `*_repaired` events are a safety net working, not a normal condition. They should be rare and each one deserves an investigation.

**Rotate the JWT secret.** Set a new `JWT_SECRET` and restart. Every access token becomes invalid (401) and every client refreshes with its refresh cookie, which is unaffected, so users stay signed in; there is no shared state to migrate. If the old secret leaked, also revoke refresh tokens: `UPDATE refresh_tokens SET revoked_at = now() WHERE revoked_at IS NULL;` (everyone logs in again).

**Suspend / lock.** Admins use `POST /admin/users/:id/suspend` and `POST /admin/courses/:id/lock`; both are audited (`GET /admin/audit-logs`).

**Reading the log.** Every request has an `X-Request-Id` that is also in the log line. Passwords, tokens, cookies, Authorization headers and message bodies are never logged; a 500 is logged with the request id, and the response never contains the cause.

**Do not** run a second backend instance (the jobs would run twice and the socket registry, throttle counters and presence are in process memory), and do not put the pooler in statement mode.

## 10. Notes for the frontend

The contract is `apps/backend/openapi.json` (also served at `/api/docs-json` outside production); every error is `{ statusCode, code, message, errors? }`: **branch on `code`, not on `message`**.

- **Tokens.** The access token (15 minutes) goes in `Authorization: Bearer`. The refresh token is an HttpOnly cookie sent only to `/api/v1/auth`. Share **one in-flight refresh** between all requests that get a 401. **Refresh before reconnecting a socket** (the handshake token must be a current access token, sent in the auth payload, never in the URL). A parallel refresh inside ~10 s answers `409 RESOURCE_CONFLICT`: retry once with the new cookie.
- **401 vs 403.** 401 = log in again / refresh. 403 `ACCOUNT_SUSPENDED` = signed out for good. 403 `INVALID_CURRENT_PASSWORD` (change-password) is a form error, **not** a session problem. 403 `COURSE_ADMIN_LOCKED` = show "unavailable"; 404 means "you may not know it exists".
- **503 `SERVICE_UNAVAILABLE`** = try again later (nothing changed). 429 = back off (`Retry-After`).
- **Private pages are rendered client-side.** Do not cache lesson content or other private responses in shared caches.
- **Chat.** Sort messages by `seq` and detect gaps (reload history with `after`). Send `clientId` as a UUID from `crypto.randomUUID()` and **reuse the same `clientId` for every retry of the same message**; the same id with another body is `409 CLIENT_ID_REUSED`. A deleted message arrives without text.
- **Markdown.** The server stores lesson Markdown **unsanitized**. The frontend must render it with raw HTML disabled or sanitized, and no `javascript:` links (this boundary is part of the contract, Section 14 of `docs/proposed-defaults.md`).
- **Courses.** Send `enrollmentPolicy` explicitly when creating a course (there is no default). Attachments are downloaded through `GET /courses/:courseId/lessons/:lessonId/blocks/:blockId/download`, which hands out a signed URL valid for 5 minutes: ask for a new one per download.
- **Registration and email.** Registration always answers 202 with one body; verification never logs in. Verification links last 24 h, reset links 1 h.
- **Admin screens** use `/admin/*` only; an Admin is an ordinary user everywhere else.

## 11. Known limitations (accepted for v1)

- **One backend instance.** Jobs, the socket registry, presence and the throttle counters are in process memory (Decision 162).
- **No account lockout**; throttling by address and email only. Slow scraping of the user search is an accepted risk.
- **A stolen access token** could link a Google account for up to 15 minutes; a single-device logout leaves that device's socket open until its next event.
- **A narrow pre-verification registration race** and suspended users counting toward group caps are accepted.
- **Deleted-message text persists** in the database and backups.
- **The `EXPLAIN` checks** run on synthetic data of tens of thousands of rows: they guard the shape of the plans, they are not a production-volume benchmark.
- **The Admin report detail returns the stored snapshot** (and only there); the live text of a deleted message is never returned.
- **Private Vimeo links** (`vimeo.com/<id>/<hash>`) are accepted but the hash is dropped, so such videos may not play. Unresolved by decision.
- **No development object store** is provided in Compose (the MinIO decision is open); point `S3_*` at an S3-compatible server you run.
- **Tag rename and delete** are not offered (only list and merge); a new audit action would be needed first.
